MCP in 60 seconds

Four ideas from MCP

Tools

Actions the model chooses to call, with a typed input schema.

scapi_execute, docs_search, cip_query

Resources

Content addressed by URI that a client can read into context. Read-only, no side effects.

skill://mcp/b2c-mcp-scapi/SKILL.md

Elicitation

The server asks the user a question mid-task. The client renders it and returns the answer.

Our Safety Mode approvals

Extensions

Optional protocol additions a server declares when it connects. Clients that don't know them ignore them.

Skills: io.modelcontextprotocol/skills

A host (IDE or chat app) embeds the model and one client per server. Our server speaks JSON-RPC to it over stdio or HTTP and never talks to the model directly.

Notes

  • Roles of control: tools are model-controlled, resources are application-controlled, elicitation is server-initiated but user-answered.
  • Everything later maps back to these four: code mode is a tool; skills are resources delivered by an extension; Safety Mode approvals are elicitation.
  • The model only sees what the host decides to put in context: tool descriptions, and whatever resources get read.
Skills · why they exist

A tool list says what exists. It doesn't say what to do.

Skills live outside the server

Skills usually live outside the MCP server: a separate repo, plugin or folder to find and install, on its own version. They drift from the server, and nobody who connects the server knows a companion skill exists.

Too big for descriptions

Tool descriptions, schemas and server instructions have to stay small: they ride along in context on every turn. A real workflow is hundreds of lines of conditional detail, needed only sometimes.

No convention

Everyone invented their own skill:// layout, with different rules for paths and sub-files.

We don't hand an agent raw SCAPI and hope. Where the right move isn't obvious, we write it down and ship it with the tools.

Notes

  • Cards one and three follow the SEP-2640 motivation (fragmented distribution, inconsistent ad-hoc conventions). Card two is our own argument: the SEP only names server instructions, but the same limit applies to tool descriptions and schemas, which also ride in context every turn. Say it as our experience, not as the SEP's words. SEP status: Final, Extensions track, created 2026-04-23.
  • An Agent Skill is just a directory with a SKILL.md (YAML name + description, then markdown) and optional references/. Progressive disclosure: the model sees descriptions first, bodies and references only when needed.
  • Our case is concrete: hundreds of operations, Admin vs Shopper auth (AmOAuth2 vs ShopperToken), OAuth scopes, and known traps like status=failed returning HTTP 400.

Docs · the knowledge underneath

3,000+ articles for developers, merchants and admins

692Developer guides: B2C, Storefront Next, Commerce API, PWA Kit, SFRA, OCAPI
1,200Salesforce Help: 626 merchant, 574 administrator
381Salesforce Help knowledge base articles
673Reference: 545 Script API classes, 70 job steps, 58 XSD schemas
63B2C tooling docs: CLI, SDK and MCP

Search: MiniSearch, a small in-memory full-text index. Words are tokenized and ranked BM25-style across title, headings, keywords and summary (title weighs most), with prefix and typo tolerance. Results are then re-ranked for the detected project: a PWA Kit repo lifts PWA Kit and Commerce API docs and demotes SFRA and Storefront Next guides.

Built so an agent can triage

  • docs_search returns summary, keywords, category and URL, so it can pick before it reads
  • For guides and knowledge base articles, Claude Haiku writes summaries and keywords at build time, so plain-language queries find the right doc
  • docs_read returns clean markdown for every article, not HTML pages, fetched online from the canonical source (not bundled)
  • Indexed by title and headings; that beat full-body search in our evals
  • Narrow by category when the question is clearly merchant, admin or developer

Notes

  • Markdown everywhere: guides are fetched as their published .md twin, Help and knowledge base articles are converted to markdown and hosted on our docs site, tooling docs are .md, and Script API classes and job steps are bundled as markdown. Agents read and quote markdown far more reliably than scraped HTML (no nav, scripts or layout noise, fewer tokens). Only the XSD schemas are not markdown, they are served as schema files through the docs_schema_* tools.
  • Ranking: MiniSearch (in-process, no service) with field boosts title 3, id 2.5, keywords 2, headings 2, summary 1.5; fuzzy 0.2 and prefix on. Class-name lookups like "ProductMgr" still come first.
  • Project-aware re-ranking: the server detects the workspace (cartridges, SFRA, PWA Kit v3, Storefront Next). Relevant categories are boosted (platform docs, OCAPI and tooling always; Script API and job steps for cartridges; PWA Kit and Commerce API for PWA Kit; Storefront Next and Commerce API for Storefront Next). Competing storefront guides get a 0.3 multiplier. It is a demotion, not a filter, so a strong exact match can still surface. Help corpora are never blanket-boosted; they are reached by category.
  • Counts come from the checked-in indexes: 692 + 1,200 + 381 + 673 (545 + 70 + 58) + 63 = 3,009.
  • Why docs matter alongside skills: a skill says what to do; docs say what a setting or error means. A merchant question like "why isn't my promotion applying" is a Help-article question, not an API one.
  • Wording rule for the knowledge-base corpus: "Salesforce Help knowledge base" only. Don't describe where it came from.
  • Online vs bundled: guides, Salesforce Help and knowledge base article bodies are fetched from the canonical URL at read time (memory + disk cache with a TTL, 10 s fetch timeout). Bundled and offline: the search indexes (about 2.7 MB for those three corpora), Script API reference, job steps, tooling docs and XSD schemas.
  • Enrichment: optional build-time step (enrich:docs), no-op without an API key, output committed as enrichment.json. Covers all 692 guides and all 381 knowledge base articles. Not applied to Salesforce Help (1,200), which carries a summary from each article's own short description, nor to the reference corpora. It improves recall for agentic queries ("configure sites.js locale currency" finds "Multiple Sites"). The index is title + headings with no body text; earlier evals favored that over full-body search. (The guides sidecar file holds 809 entries; 117 are stale leftovers.)

Intro to Code Mode

Let the model write code, not tool calls

Tool calling: every hop passes through the model

sequenceDiagram
    participant M as Model
    participant T as Tools
    M->>T: call A
    T-->>M: result A
    M->>T: call B (copy from A)
    T-->>M: result B
    M->>T: call C (copy from B)
    T-->>M: result C

Code Mode: the code is the plan

sequenceDiagram
    participant M as Model
    participant X as Sandbox
    participant T as Tools
    M->>X: one program
    X->>T: call A
    T-->>X: result A
    X->>T: call B (uses A)
    T-->>X: result B
    X-->>M: final answer only

Cloudflare applied it to its own API: an MCP server with just two tools, search() and execute(), over an OpenAPI spec. By their numbers, 2,500+ endpoints cost about 1,000 tokens of context.

Cloudflare, who introduced the pattern: blog.cloudflare.com/code-mode · blog.cloudflare.com/code-mode-mcp · developers.cloudflare.com/agents/tools/codemode · codemode/openapi

Notes

  • Why not one tool per operation: hundreds of Admin and Shopper operations bloat context and still miss tenant c_* fields and custom APIs (live contracts from the Schemas API cover those). Tasks are multi-step, and every hop is a model round trip. Dedicated tools are still preferred when one fits; code mode is the "no specific tool fits" path.
  • Say it up front: Code Mode is Cloudflare's idea and name. We are applying the pattern to SCAPI, not claiming it.
  • Why it works, in their words: models have seen huge amounts of real code but few real tool calls (tool-call tokens exist mostly in synthetic training data), and chained tool calls waste tokens copying intermediate results through the model.
  • Their sandbox: V8 isolates (Dynamic Workers), no network, only bindings; the supervisor holds the tokens so generated code cannot leak keys. Ours: a local Node child process, same trust split, but explicitly not a security sandbox.
  • Shared vocabulary: search/execute, codemode.search/describe, snippets, approvals. Cloudflare's docs list approvals and replay in their durable runtime; we park a live worker instead of replaying (later slides).
  • The 1,000 token and 2,500 endpoint figures are Cloudflare's claims about their API, not ours. Their docs still label Code Mode experimental.
  • Sources: blog.cloudflare.com/code-mode/ · blog.cloudflare.com/code-mode-mcp/ · developers.cloudflare.com/agents/tools/codemode/ (and /openapi/)
Our implementation · SCAPI

The agent writes a small async function. We run it.

Read the skill first. Both tools refuse to run until the agent has read the companion b2c-mcp-scapi skill and passes skillRead: true. The skill is what teaches it auth, scopes and the traps.

1 · scapi_search: find the operation, its path and auth
async () => Object.entries(spec.paths)
  .flatMap(([path, ops]) => Object.entries(ops).map(
    ([method, op]) => ({operationId: op.operationId, method, path,
                       security: op.security})))
  .filter(o => /^(create|update)Product$/.test(o.operationId))
2 · scapi_execute: call it
async (input) => {
  const path = '/product/products/v1/organizations/'
             + '{organizationId}/products/' + input.id;
  const r = await scapi.request({method: 'GET', path});
  if (r.status === 404) {
    await scapi.request({method: 'PUT', path,
                         body: {id: input.id,
                                name: {default: input.name}}});
  }
  return (await scapi.request({method: 'GET', path})).data;
}

scapi_search

Find the right operation: run code over the OpenAPI contracts (spec) for operationId, path, inputs, auth and scopes. Offline by default. Can't make requests. Want the raw OpenAPI document instead? scapi_schemas_list fetches it live.

scapi_execute

Same sandbox plus scapi.request, auth, codemode. Governed by Safety Mode.

scapi_snippet_save

Keep a finished run as a reusable user/… snippet. We ship builtin/ ones for common workflows; the agent can read and adapt them, not just run them as-is.

For the full OpenAPI document with no code, scapi_schemas_list with includeSchemas plus family/name/version fetches it live from the tenant (needs the sfcc.scapi-schemas scope; also the route for custom APIs and tenant c_* fields). Not a bundled/offline path.

  • The only exits from the function are scapi.request, auth.* and codemode.*.
  • This is the bridge from skills to code mode: the tool descriptions say it, and a missing skillRead returns SCAPI_SKILL_REQUIRED with the URI to read. It is an honor-system gate (the server can't verify the read), but it reliably routes the agent through the skill. Skills · how tools lean on them

Three strengths of nudge

Required: a gate

scapi_search, scapi_execute and cip_* take skillRead: true. Without it the call fails and names the file to read.

SCAPI_SKILL_REQUIRED: Read skill://mcp/b2c-mcp-scapi/SKILL.md …

Suggested: a pointer

Tool descriptions and server instructions point at a skill: config prerequisites for cartridge tools, the debugger workflow, which tool fits which job.

Nothing enforces it.

Reactive: a hint in the error

An auth or scope failure comes back with skillReferences: a URI and the exact section to read.

Detail for a condition we saw, never a prerequisite.

Strictest where the cost of guessing is highest: arbitrary code against live APIs. skillRead is an honor-system flag; it records that the model claims to have read it.

Notes

  • The gate is z.literal(true) with a custom error, so the failure message teaches the fix and the model self-corrects in one retry.
  • Be upfront: nothing verifies the read happened. It is a strong prompt, not a security control. Safety Mode is the actual control.
  • Suggested pointers live in tool descriptions (cartridges, debugger) and the server instructions. Reactive ones come from MCP_SKILL_REFERENCES in skill-references.ts.
  • Design stance in that file: references are "optional detail for an observed condition; never a prerequisite or approval".

The worker

A guardrail, not a fortress

What it does restrict

  • Node --permission: no filesystem, subprocesses, worker threads, native addons
  • fetch / WebSocket replaced with a thrower
  • No credentials: env scrubbed, tokens stay in the parent
  • Must await every call before returning; JSON result only

The source says it plainly: "local execution, not a security sandbox." The threat model is a cooperative agent that makes mistakes.

Safety Mode

One policy format, resolved per execution

Evaluation order

1 Temporary allows (approved requests)

2 Rules in order, first match wins: allow · block · confirm

3 Level default: NONE · NO_DELETE · READ_ONLY

A level violation becomes confirm if confirm: true, else block. An explicit block rule is never overridden.

Where the policy comes from

  • dw.json safety for the selected instance
  • Global safety.json
  • SFCC_SAFETY_LEVEL / _CONFIRM / _CONFIG

Strictest level wins · instance rules before global rules · any source can enable confirm. Off by default.

{
  "safety": {
    "level": "READ_ONLY",
    "rules": [
      {
        "method": "PUT",
        "path": "/product/products/v1/organizations/*/products/*",
        "action": "confirm"
      }
    ]
  }
}

Notes

  • Every request goes through one per-request SafetyGuard in the parent; an approval never exempts a concurrent or later request. Escape hatch: auth.accountManager() / auth.slas() can export a token for an external client, and that use is outside Safety Mode.
  • Same config format for CLI, IDE extension and MCP. Code mode needs no extra setup.
  • POST-based searches (e.g. job-execution-search) need an explicit allow under READ_ONLY.
  • This example: reads flow, product PUTs prompt, everything else that writes is blocked.
MCP concept · elicitation

How does a server ask the user a question?

MCP 2025: one call, kept open

sequenceDiagram
    participant U as User
    participant C as Client
    participant S as Server
    C->>S: tools/call
    S->>C: elicitation/create
    C->>U: show form
    U-->>C: answer
    C-->>S: answer
    S-->>C: tool result

The server sends a request to the client while the tool call is still open. Needs a long-lived, two-way connection.

MCP 2026-07-28: stateless, two calls

sequenceDiagram
    participant U as User
    participant C as Client
    participant S as Server
    C->>S: tools/call
    S-->>C: input_required + requestState
    C->>U: show form
    U-->>C: answer
    C->>S: tools/call + requestState + answer
    S-->>C: tool result

The server never calls the client. The first call ends with "I need input"; the client calls again carrying the state back. Nothing is held open.

Same human prompt, same word: elicitation. What changed is the plumbing, so any server instance can serve the retry. We serve both: one handler, and for 2025 clients a bridge turns input_required into a real elicitation/create. A client with no elicitation support never gets a write: nothing is sent.

Notes

  • Stateless means the protocol keeps no per-connection state. requestState is how the server hands its state to the client and gets it back.
  • Why it changed: server-to-client requests need a persistent bidirectional channel, which fights load balancers and serverless.
  • "Input request" is the umbrella: elicit (form), elicitUrl, createMessage (sampling), listRoots. "Elicitation" is still what users see.
  • For most servers the state in requestState is small and self-contained. Code mode's state is a live worker process, so ours is a signed pointer to something held in server memory.
  • Our handler can't tell which era it's in: same requestState path, same registry. Legacy bridge details: SDK shim, capped at 20 rounds per call; the patched SDK's roundTimeoutMs: 0 removes the server-side timer. Clients may impose their own timeout on a long-open prompt. Without form elicitation: SCAPI_CONFIRMATION_UNSUPPORTED.
  • The old in-handler elicitInput() is deprecated and throws on a 2026-07-28 request.
Approval flow

Three layers of waiting

sequenceDiagram
    autonumber
    actor U as User
    participant C as MCP client
    participant S as MCP server
    participant W as Worker
    participant API as SCAPI
    U->>C: "Update the product name"
    C->>S: tools/call scapi_execute (code)
    S->>W: spawn, run the agent's code
    W->>S: IPC request (PUT /product/...)
    Note over S: policy says confirm.
Park the request, pause the 30s clock
    S-->>C: input_required + elicitation (requestState)
    Note over W: still awaiting its IPC reply
    C->>U: Accept / Decline / Cancel
    U-->>C: Accept
    C->>S: tools/call (same args + requestState + answer)
    Note over S: verify token + args,
resume the parked request
    S->>API: PUT (re-checked, unchanged)
    API-->>S: 200
    S-->>W: IPC reply
    S-->>C: tool result (after the program finishes)

Notes

  • The three layers: the worker waits on an unanswered IPC reply; the parent holds a parked promise; the tool call is not waiting at all, it already returned.
  • Setup: the worker is halfway through a loop holding variables and earlier results. Replaying would resend earlier writes; blocking the tool call is impossible because the newer protocol has no server-to-client request channel. So: park the work, return a question.
  • Resume, if asked: the retry carries a signed requestState token (execution id + round + HMAC over the args). The server finds the parked worker, and any change to code, input or target is rejected. The model never builds these calls.
  • Your question answered: the request promise is blocked; the tool call is not. Elicitation is driven from the MCP server (parent), never the worker. The worker is not signalled.
  • Empty form schema on purpose: the client's own Accept / Decline / Cancel carry the decision.
  • The 30 s runtime budget only counts running time; pauseTimeout stops it while the prompt is open. Prompts have no server-side deadline.
  • The prompt result also carries _meta: executionId, status, operations so far.
What the user sees

Exact request, pinned

Approve SCAPI operation: createProduct Organization: f_ecom_zzpq_013 PUT /product/products/v1/organizations/…/products/test-001 Body: { "name": "Test product", "onlineFlag": false } Safety Mode requires approval. Accept sends this request only; declining stops this execution. No earlier writes. Execution: 4b2e…
DeclineCancelAccept
  • Preview: pretty-printed, ≤5 lines / 400 chars, truncation marked, credential-like keys redacted
  • Approval covers the full original body
  • URL, method and body are re-checked right before dispatch: SCAPI_APPROVAL_MISMATCH if anything changed
  • Accepting one request never approves the next, even an identical one
  • Decline or cancel stops the whole execution. Earlier writes stay (no rollback); the result lists what completed, and what was not_sent or unknown

Notes

  • Ledger statuses: completed, failed, awaiting_confirmation, in_flight, not_sent, unknown. "Dispatched" is marked right before the network call, so a kill can honestly say not_sent vs unknown (might have applied). Decline gives SCAPI_APPROVAL_DECLINED, dismiss gives SCAPI_APPROVAL_CANCELLED; also explicit action:"cancel", client abort, timeout, shutdown. Last 50 finished executions are retained so late retries get the stored result. 4 active executions per server.
  • Args are structuredCloned at entry so the code can't mutate the request while the prompt is open.
  • Illustrative values in the mock; real text comes from ScapiExecution.confirm().
  • The client's generic "allow this tool?" dialog is separate and does not approve a specific request.

  • Skills make code mode safe to hand over: the agent knows the traps before it writes code
  • Code mode makes skills executable: a runbook step can be one bounded program
  • Docs supply meaning, for merchant and admin questions no API answers
  • The debugger lets the agent observe what actually ran, closing the agentic inner loop
  • Safety Mode and elicitation keep the human in the loop

Notes

  • Q&A: honest limits. Not a hostile-code sandbox (cooperative agent; network blocking is a JS override, --permission coverage of raw https untested). Safety Mode governs requests through scapi.request, not the agent's other tools or exported tokens. Off by default (level NONE); no rollback by design, the ledger says what happened. Needs a client that can prompt; state is in-memory per stdio server. For hard enforcement, sandbox the server with the client secret out of the agent's environment.
  • What's next: other MCP tools get the same policy via SDK client middleware. block works; confirm fails with SafetyConfirmationRequired since there is no approval UI. Simple extension: catch it in runWithSafety, return an input_required elicitation, verify the token on retry, temporarilyAllow, re-run. Safe for single-request tools; multi-write tools need care since a re-run repeats earlier steps. Not prototyped.
  • Say these before someone asks. Docs: docs/guide/safety.md, docs/mcp/security.md, docs/guide/agent-sandboxing.
  • Say it plainly: none of these was designed as a combined system, and each is useful alone. The properties on the right appear when they meet.
  • Example thread: the order-failure runbook (skill) tells the agent SCAPI can't filter failed orders and to use the OCAPI fallback; code mode runs the bounded queries; docs explain the failure code; any write is confirmed by a person.
  • Not claiming autonomy: the human approves writes, and skills are guidance, not guarantees.
